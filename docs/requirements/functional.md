# Functional requirements

Every requirement has a stable ID, a priority and an acceptance check. Unless marked otherwise, requirements here are **P0**. All server commands go through the [single data path](../architecture.md#one-data-path); "blocked" always means nothing was sent to the server.

### Connection error categories (FR-CN10)

| Category | Typical cause | Message names |
| --- | --- | --- |
| `DNS_FAILED` | Host can't be resolved | The host |
| `CONNECTION_REFUSED` | Nothing listening | Host and port |
| `TIMEOUT` | Connect or handshake exceeded the timeout | Which phase (TCP — "TCP and TLS" for a TLS profile, AUTH, tunnel) and the timeout |
| `TLS_UNTRUSTED` | Chain doesn't verify against system or custom CA | Issuer, and that a custom CA can be selected |
| `TLS_HOSTNAME_MISMATCH` | Certificate doesn't match the server name | Expected name and certificate names; suggests SNI override |
| `TLS_HANDSHAKE_FAILED` | Protocol mismatch, client cert required or refused, or server not speaking TLS | "Server may not be using TLS" when a plain `PING` to the same port gets a RESP reply ([Architecture](../architecture.md#tls)); "requires a client certificate" when the profile has none, "rejected the client certificate" when it has one; the `errSSL` status |
| `NOT_TLS_EXPECTED` | TLS server reached without TLS: it answered with a TLS record | Suggests enabling TLS |
| `TLS_CA_UNAVAILABLE` | The custom CA file is missing, unreadable, not a regular file, over 4 MiB or holds no readable certificate (FR-CN04); nothing is sent | The file's path and the reason |
| `TLS_CA_CHANGED` | The custom CA file's SHA-256 changed and the user declined the new fingerprint (FR-CN04); nothing is sent | The file's path |
| `AUTH_FAILED` | `WRONGPASS`, `NOAUTH`, `ERR invalid password`, user disabled | Username (never the password); for `NOAUTH`, that a password is required |
| `PERMISSION_DENIED` | `NOPERM` during handshake (e.g. `SELECT`, `INFO`) | The command the ACL user can't run |
| `TUNNEL_FAILED` | ssh exited, forward failed, host key declined, or the tunnel settings were invalid (nothing runs) | ssh exit status and sanitized last stderr line; the SSH destination; a fix chosen from ssh's message (host key, permission denied, forwarding, DNS) |
| `PROTOCOL_ERROR` | The port doesn't speak RESP | "This port doesn't look like a Redis server" |
| `DB_OUT_OF_RANGE` | `SELECT` fails | The index and the server's database count (from `CONFIG GET databases`, when permitted) |
| `CONNECTION_FAILED` | The connection dropped during the handshake, or another OS error | Host and port, the handshake step; suggests TLS when the server may require it |
| `SERVER_ERROR` | Any other error reply during the handshake | The step and the server's error code (scrubbed text in details) |

## 3. Value editors

Common rules for all editors:

- Values are bytes. The viewer has a small **Text / JSON / Hex / Raw** switch at its top right (JSON is chosen automatically when the value parses, with a "✓ Valid JSON" note). For hashes, lists, sets, zsets and streams, selecting a row opens that element in the viewer under the table. Viewers: **Text** (UTF-8, invalid bytes shown escaped), **JSON** (pretty-printed, validated, with error line/column), **Hex** (offset, hex, ASCII), **Raw** (redis-cli escaped). The selected viewer is remembered per key pattern for the session.
  - JSON is chosen automatically only for an object or array that parses (`42` or `"x"` open in Text). Pretty-printing keeps key order and the tokens as written (two-space indent); validation is strict RFC 8259 with errors as "Line 3, column 5: …" (columns count characters) and nesting deeper than 512 levels reported as an error.
  - Text shows valid UTF-8 as is. A value with invalid UTF-8 or a control character other than tab and newline is shown escaped as a whole: each such byte reads `\xNN` and `\` doubles, so editing in Text decodes back to the same bytes; an incomplete escape stays literal.
  - Raw shows the double-quoted redis-cli form and parses edits like a redis-cli quoted argument (`\xNN`, `\n \r \t \b \a`, `\c` → `c`); text that doesn't parse keeps the last good value and blocks Save with the reason. Hex is read-only (16 bytes a line, two groups of eight, like `hexdump -C`) and formats lines as they scroll into view.
  - The key pattern is the key up to its last separator plus `*` (`user:42` → `user:*`), or the key itself without a separator; choices are held in memory per tab and never persisted. Text views never apply automatic substitutions (quotes, dashes, replacements, spelling).
- Large values load in bounded pages; partial content is marked "Showing 1–500 of 82,113" and editing operates only on loaded items.
- Edits are explicit: change → **Save** (⌘S) / **Revert** (⌘Z before save). A floating bar ("1 unsaved change · Revert · Save") appears at the bottom of the editor **only** while there are unsaved changes; changed rows get a small accent dot. Unsaved changes are confirmed on close.
- Save **preserves TTL** (`SET … KEEPTTL` for strings; collection edits don't touch TTL).
- Concurrency: whole-value saves use `WATCH key` + `MULTI/EXEC`; if the key changed since it was loaded, the save fails with `CONFLICT`, writes nothing and offers Reload (the server's value replaces the draft) or Overwrite (the same writes without the guard). A save whose connection drops reports that its outcome is unknown and re-reads the value; it is never re-sent. ⌘S and ⌘Z are File → Save Changes / Revert Changes, enabled only while the save bar shows.
- Read-only profiles show editors in view mode: "· Read-only" with a lock in the metadata line, no Add/Save controls, and write actions disabled in the ⋯ menu. Viewing (including the viewer switch) is unchanged.

| --- | --- | --- | --- |
| FR-ED01 | String | View and edit with Text, JSON, Hex and Raw viewers; save with SET preserving TTL. Invalid JSON can be saved only from Text view (JSON view blocks it with the parse error). |
| FR-ED02 | Hash | Field/value table with sorting by field and local filter (loaded fields, by name); add, edit value, rename field (HSET new + HDEL old in one MULTI), delete fields. | FR-ED03 | List | Indexed table paged with `LRANGE` (500 per page, `LLEN` first; Load more continues), jump to index (the page starting at that 0-based index; an index past the end says how many items there are), edit by index (`LSET`), push and pop at head or tail (`LPUSH`/`RPUSH`/`LPOP`/`RPOP`), insert before/after (`LINSERT`), delete by index (LSET to a random sentinel + `LREM 1` in one MULTI). Removals carry no guard reads (removing a member already gone is harmless), so only a change between `WATCH` and `EXEC` is a `CONFLICT`. A member's bytes are its name, so the viewer shows it read-only (change = remove + add). | Adding an existing member reports "already a member" (SADD returned 0). A 1M-member set opens showing the first `SSCAN` page; `SMEMBERS` is never sent for it. |
| FR-ED05 | Sorted set | Member/score table **sorted by score** (ascending/descending toggle; ties by member bytes, as Redis orders them), paged by score 500 at a time with `ZRANGE … BYSCORE [REV] … WITHSCORES LIMIT` where the probe finds it (6.2+, FR-CN12) or `ZRANGEBYSCORE` / `ZREVRANGEBYSCORE`; a page starts at the last score loaded, inclusive, and skips (`LIMIT`) the members with that score already loaded, so members sharing a score are neither missed nor repeated. Reversing a paged set reloads it from the other end (enabled only while nothing is unsaved); a fully loaded one re-sorts. Pattern search with `ZSCAN … MATCH` (COUNT 500, at most 8 rounds per page, "Search more") shows the matches in place of the pages. The table keeps the loaded order until the save, whose read-back asks `ZSCORE` about the touched members only. Add (`ZADD`) and increment (`ZINCRBY`) run at once, enabled only while nothing is unsaved; adding an existing member updates its score and says so. Scores show full double precision (the shortest text that reads back as the same double; whole numbers without a fraction) and `inf`/`-inf`; input accepts numbers, `inf`, `+inf`, `-inf`. The viewer shows the selected member read-only. | A 100k-member zset shows the lowest scores first and pages forward; changing a score moves the row to its new position after save. On Redis 6.0 pages use `ZRANGEBYSCORE`. |
| FR-ED06 | Stream | Read-only entry table (ID, then the entry's field/value pairs on one line) paged with `XREVRANGE` (newest first, the default) or `XRANGE` (oldest first; the ID header reverses the order), 500 per page with Load more. After the add the newest page is read back, so the new entry shows at the top, selected; a lost reply is never re-sent (the read-back shows whether it landed). | Adding an entry with `*` shows the server-assigned ID at the top. On Redis 6.0 a page after `1245-0` (newest first) starts at `1244-18446744073709551615`. Entries can't be edited in v1; `XDEL` and consumer groups are P1. |

### Common key actions

| ID | Requirement | Acceptance check |
| --- | --- | --- |
| FR-ED10 | Rename a key with `RENAMENX` by default. If the target exists (`RENAMENX` replied 0, nothing changed), ask whether to overwrite, then use `RENAME`; the confirmation covers only that key and target. Keys can't be renamed to an empty name or their current name. Rename waits until nothing is unsaved (it reopens the key under its new name). ## 5. Safety

| ID | Requirement | Acceptance check |
| --- | --- | --- |
| FR-SF01 | **Read-only mode** per profile blocks every write (catalog `write` flag, scripts that may write, unknown commands, admin commands) in editors, the console, bulk actions and the new-key sheet. | FR-SF02 | Production chrome: a 28 px strip under the tab bar, deep maroon (light `#7A1A14`, dark `#4A1F1C`), with centered text "Production · Read-only" ("Production" alone when writes are allowed). | FR-SF03 | Typed confirmations for destructive operations: deleting more than one key (type the number of keys), bulk delete by pattern (type the pattern), **FLUSHDB** (type the database, e.g. `db3`), **FLUSHALL** (type the profile name). | FR-SF04 | Multi-key delete from a selection uses `UNLINK` in batches of 500, after FR-SF03 confirmation; the confirmation covers exactly the selected keys. | FR-SF05 | **Bulk delete by pattern**: `SCAN MATCH <pattern> COUNT 1000` (plus `TYPE` when the browser's type filter is a core type) + `UNLINK` in batches of up to 1,000 keys on the `job` connection. While running it shows a progress bar, one line ("1,221,000 deleted · about a minute left") and **Cancel**, which lets the batch in flight finish and sends nothing more; Escape doesn't close it. The final report gives the deleted count, scanned SCAN pages, matched keys and the rate, and says that keys created or renamed during the run may remain. Each key is checked against the pattern again before it is sent; a failed batch stops the run like FR-SF04 (a lost reply is never re-sent). Patterns of only `*` are refused (by the job and by the policy); use FLUSHDB. The browser rescans when the run ends. | Cancel stops within one batch; the report states the deleted count and that keys created during the run may remain (SCAN guarantees). | FR-SF06 | Optional throttle for bulk jobs (default 10 batches/s, configurable 1–100, or unthrottled) to protect production latency. | FR-SF07 | Write commands on Production profiles that aren't read-only show a non-blocking "Writing to PRODUCTION" banner in the editor and console the first time per tab: on the first command that may change data and passes the policy, a dismissible line above the editor (the console shows it too). | FR-SF08 | `KEYS` and other O(N) commands on large databases (`KEYS`, `SMEMBERS`/`HGETALL`/`LRANGE 0 -1` on > 10,000 elements, `FLUSHALL` without `ASYNC`) warn in the console with the size before sending. The size is read first through the data path (`DBSIZE`, `SCARD`, `HLEN`, `LLEN`, `INFO keyspace`); "large" is more than 10,000 keys or elements for each of them; `LRANGE` warns on the span it reads (`0 -1`, or any range covering more than 10,000).
