# macOS support

Keel is a macOS-only application.

## Supported platform

- **MAC-01 (P0):** macOS 14 Sonoma minimum, and every later public major version through the current stable release. Each release publishes the matrix actually tested. Beta OS releases are best effort.
- **MAC-02 (P0):** native Swift, built as Universal 2: arm64 and x86_64 slices built natively and combined with `lipo`. Running under Rosetta doesn't count as Intel qualification.
- **MAC-03 (P0):** SwiftUI for chrome and settings; AppKit for virtualized key lists, tables, the console text view and the responder chain. No Electron, webview or browser runtime.

## Native behavior

- **MAC-04 (P0):** integrates with the menu bar (menus built from current shortcut bindings), the standard About Keel panel (version, © Bearstouch with a link to bearstouch.com), Settings (⌘,), the Dock, standard hide/minimize/full screen, the Window menu, standard open/save panels, system appearance, notifications (finished bulk jobs, only when the app is in the background), and Services where meaningful (copy key name).
- **MAC-05 (P0):** multiple native windows, each with Keel's own tab bar. macOS automatic window tabbing is disabled; every tab belongs to Keel's model. Window frames restore constrained to the available displays.
- **MAC-06 (P0):** closing a window with unsaved value edits asks once; closing a window with a running bulk job asks whether to cancel it. Quitting with running bulk jobs offers **Cancel Jobs and Quit** / **Don't Quit**; there's no background continuation after quit.
- **MAC-07 (P0):** Retina and non-Retina, display changes, full screen, Stage Manager and Split View; small windows keep minimum sizes for the key list and editor and collapse the sidebar instead of overlapping.

## Distribution, signing and updates

- **MAC-08 (P0):** distributed directly as a signed DMG (not the Mac App Store), Developer ID signed with the hardened runtime, notarized and stapled. The app and the bundled `keel-askpass` helper (`Contents/Helpers`) are signed; Sparkle's helpers (`Autoupdate`, `Updater.app`) are signed inside-out as Sparkle documents, then the framework, the helper and the app; Keel isn't sandboxed, so Sparkle's XPC services are left out of the bundle. Ad-hoc builds (never distributed) are signed without the hardened runtime, because library validation can't load an embedded framework without a Team ID. Automatic updates through Sparkle 2 (INT-11): EdDSA-signed appcast, user-confirmed install, daily check that can be turned off. Gatekeeper acceptance is verified on a clean machine (**pending** until observed).
- **MAC-09 (P0):** not sandboxed. Keel must run `/usr/bin/ssh`, read `~/.ssh/config`, and reference certificate files anywhere the user keeps them. Entitlements: none beyond the hardened runtime defaults (no JIT, no unsigned memory, no library validation exceptions). A sandboxed build would need its own feasibility decision.
- **MAC-10 (P0):** release decisions are recorded in `release/manifest.json` (version, bundle ID `com.bearstouch.keel`, minimum macOS, architectures, helpers, Sparkle feed URL and public EdDSA key) and checked by `KeelReleaseTests`. `scripts/package-release.sh` produces `dist/Keel.app`, `dist/Keel-<version>.dmg`, the Sparkle archive and `dist/release-evidence.json` (which includes the latest benchmark evidence, `.build/bench/evidence.json`, under `performance`); ad-hoc unless `KEEL_SIGN_IDENTITY` / `KEEL_NOTARY_PROFILE` are set (`KEEL_NOTARY_KEYCHAIN` when the profile isn't in the default keychain); the EdDSA signature needs `KEEL_SPARKLE_KEY_FILE` or `KEEL_SPARKLE_ACCOUNT`. The app's `Info.plist` is `release/Info.plist` with both versions set from the manifest (`X.Y.Z` only; `CFBundleVersion` equals it, so Sparkle orders updates by it). SwiftPM's resource bundles go to `Contents/Resources`, where KeelCore and KeelUI look first (`Bundle.packagedResources`).
  - **Evidence.** `release-evidence.json` records each check in the manifest's `releaseChecks` as `passed`, `failed` or `skipped`, with a detail: `manifest` (artifacts, Info.plist identity, minimum OS, icon, version and the update keys), `architectures` (arm64 and x86_64 in Keel, `keel-askpass` and Sparkle's binaries), `minimumOS` (`minos 14.0` in every slice of Keel and `keel-askpass`), `signature` (`codesign --verify --deep --strict`), `hardenedRuntime`, `entitlements` (none), `launch` (the signed app is still running 5 s after `--fixture` launch), `developerID`, `notarization` (app and DMG `Accepted`), `stapling`, `gatekeeper` (`spctl` on the app and the DMG), `updateSignature` (the archive's EdDSA signature verifies against the manifest key and a tampered copy doesn't), `feedSignature` (the appcast is signed and verifies), `checksums` (`SHA256SUMS.txt` for the DMG, archive and appcast) and `performance` (the benchmark verdict; a run of another commit, a dirty tree or with skipped groups counts as skipped). It also holds the channel and the checksums. Any failed check — a rejected or failed notarization included — exits the script with status 1. The channel is `release` only when every check passed; anything skipped (ad-hoc, signed but not notarized, no EdDSA key, no benchmark) makes it a `prerelease`. `ReleaseChecklist` (KeelRelease) and `scripts/release-evidence.py` apply the same rules, and the tests run both on the same evidence.
- **MAC-11 (P0):** the release workflow (`.github/workflows/release.yml`) pins actions to commit SHAs, runs the tests and (on tags) the benchmarks, packages through `package-release.sh` — which verifies signature, hardened-runtime flag, both architectures, minimum OS and `spctl` — and publishes the DMG, the Sparkle archive, the appcast, `SHA256SUMS.txt` and the evidence on a GitHub release, marked pre-release unless the evidence channel is `release`.

## Files, credentials and permissions

- **MAC-12 (P0):** durable configuration in `~/Library/Application Support/com.bearstouch.keel/` (`.dev` for development builds, override with `--state-directory`); disposable data in Caches; tunnel and askpass sockets in an owner-only directory in the per-user `$TMPDIR`. Files `0600`, directories `0700`.
- **MAC-13 (P0):** secrets in the login Keychain (services in [Architecture](architecture.md#keychain-items)), *when unlocked, this device only*. Private-key contents are never written to files.
- **MAC-14 (P0):** **Local Network privacy** (macOS 15+): connecting to LAN servers triggers the system Local Network prompt; `Info.plist` includes `NSLocalNetworkUsageDescription` ("Keel connects to Redis servers on your local network that you configure."). A denied permission is detected and explained with a link to System Settings → Privacy & Security → Local Network, instead of a generic timeout.
- **MAC-16 (P0):** no root helper, no launchd agent or login item, no kernel or system extensions. Keel never asks for Accessibility, Screen Recording, Full Disk Access or Input Monitoring. Notifications permission is requested only when the user first enables a notification-producing feature (job completion).
- **MAC-17 (P0):** one instance per user per identity; opening Keel again brings the existing instance forward. The installed app and development builds (`com.bearstouch.keel.dev`) are separate identities with separate state and locks, so both can run at once.
  - **Lock.** Each state folder has its own lock: `instance.lock` (0600, opened without following links) held with an exclusive `flock` from before any state is read until the process ends, so a crash releases it and a leftover file never blocks a launch. The installed, development, `--state-directory` and `--fixture` folders each lock separately. A symlink, folder or another user's file at the lock path refuses the launch (exit 73).
  - **Second launch.** A process that finds the lock held activates the running instance (the PID recorded in the lock file, only when it is the same app) and exits with status 75 (`EX_TEMPFAIL`) without touching any state. Opening the installed app from Finder or the Dock is already routed to the running copy by LaunchServices; the lock covers `open -n`, a second binary and `swift run`.
  - **Acceptance.** `InstanceLockTests`: a second lock on the same folder is refused with the owner's PID, a released or dropped lock is free again, separate folders lock separately, and a symlink at the lock path is refused without creating its target.

## Input and text

- **MAC-18 (P0):** native text input everywhere: IME composition, dead keys, emoji, right-to-left text in values; the console and editors use `NSTextView` so system text services work. All configurable shortcuts include ⌘ (⌃ alone is reserved for console editing keys such as ⌃R, ⌃L, ⌃A/⌃E).
- **MAC-19 (P0):** bundled fonts are registered for the Keel process only: Inter (Regular, Medium, SemiBold; OFL 1.1) for all interface text, and JetBrains Mono (Regular/Bold/Italic/Bold Italic) for keys, values and the console. If a bundled font fails to load, Keel falls back to the system font (or the system monospace font) with no loss of function.

## Installation, upgrades and removal

- **MAC-20 (P0):** install by dragging `Keel.app` from the DMG to Applications. No installer package, no writes to system directories, no shell startup file edits.
- **MAC-21 (P0):** upgrades through Sparkle or by replacing the app; persisted formats are versioned and migrated with backups; newer formats open read-only and are never overwritten. Downgrades aren't supported.
- **MAC-22 (P0):** uninstalling = deleting the app. Help → **Remove Keel Data…** lists and deletes the state directory and Keel's Keychain items (all three services), after a confirmation. It never touches SSH keys, SSH configuration, known-hosts files, Trellis data or Redis servers. The Keychain items are shared by every run of Keel on the Mac whatever its state folder, and the confirmation says so. A `--fixture` run keeps its secrets in memory and never reads or writes the Keychain, so there it removes the run's state folder only: no Keychain item and no preference key.
  - The plan (`DataRemovalPlanner`, KeelRelease) is an allow-list: in the state folder only regular files with Keel's names (`<file>.json`, `<file>.backup.json`, `<file>.corrupt.<UUID>.json`, `<file>.unreadable.<UUID>.json`, `.<file>.<UUID>.tmp` for each persisted file, and `.DS_Store`), each removed with `unlink`; the folder itself with `rmdir` only when nothing else is in it (anything else is listed and kept). A state folder that is a symlink, the home folder or above it, or in `~/.ssh` is refused. Keychain: every generic password of `Keel Connection`, `Keel TLS` and `Keel SSH Host` (shared by all Keel copies on the Mac); imported client identities stay in the login keychain. Preferences: Keel's `keyboardShortcuts` key and the keys Sparkle keeps in Keel's defaults (`UpdatePolicy.sparklePreferenceKeys`: last check time, skipped version and the like).
  - The confirmation lists each group (Cancel is the default); **Remove and Quit** quits, and the removal runs after the windows and settings are flushed (window saves then stop) and the tunnels are closed, so no pending save brings a file back; the plan is computed again at that point with the same allow-list, so files the flush created (a first backup) go too. Whatever couldn't be removed (a locked Keychain, a permission error) is listed before the app exits.

## Release verification matrix

| Area | Required evidence |
| --- | --- |
| OS and architecture | Cold launch and the acceptance scenario on macOS 14 and the current release, on Apple silicon and Intel |
| Servers | Integration matrix (INT-01) green, plus a manual run against one managed TLS service |
| Connections | TLS custom CA, client cert, skip-verify banner, SSH tunnel with known/unknown/changed host key, password and agent auth, Local Network prompt |
| Browser | 1M-key performance targets (NFR-PF01–PF08, NFR-RS01) with recorded evidence: `.build/bench/evidence.json` from `scripts/bench-browser.py`, copied into `release-evidence.json` |
| Safety | Read-only protocol trace, typed confirmations, bulk delete cancel, production chrome |
| Accessibility | VoiceOver pass, keyboard-only pass, Increase Contrast, Reduce Motion |
| Security | Gatekeeper, signing, notarization, Sparkle EdDSA verification, no secrets in files or logs, no unexpected network traffic |
| Lifecycle | Quit with jobs, crash recovery, restore of windows and tabs, data removal |
